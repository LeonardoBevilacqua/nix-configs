# Migrating installation to repository

The initial configuration is always generated in `/etc/nixos`, generating the `configuration.nix` and `hardware-configuration.nix`. We can also include `flake.nix` in case we want to pin the derivation with a lock file.
This repository use the dendritic pattern, so migrating the files to the repository requires some adjustments.

## Repository overview

The repository is a **dendritic flake**: files under `modules/` are auto imported by `import-tree` and each contributes to `flake.modules.*`. Adding a host means wiring up four things:

|  Concern                              | File                                                 
| ---                                   |---                                                   
|  Host NixOS module                    | `modules/hosts/<host>/default.nix`                   
|  Home Manager integration (optional)  | `modules/hosts/<host>/home-integration.nix`          
|  Machine hardware config              | `modules/hosts/<host>/_hardware-configuration.nix`   
|  Flake output registration            | `modules/hosts/configurations.nix`                   

The leading underscore on `_hardware-configuration.nix` is **not cosmetic** - see [Pitfall #1](#1.-untracked-files-are-invisible-to-flakes).

## Step by step

1. Create the host directory, with ` mkdir -p modules/hosts/<host>`, replacing `<host>` with a short name, like `laptop` or `desktop`.
2. Copy the `hardware-configuration.nix` into the repo with a leading underscore, with `cp /etc/nixos/hardware-configuration.nix modules/hosts/<host>/_hardware-configuration.nix`
    - **Do not edit this file by hand.** If you must, only add lines. Never comment out existing `boot.*` or `fileSystems.*` entries. See [Pitfall #6](#6.-commented-out-lines-in-hardware-configuration.nix-can-break-the-boot-without-breaking-the-build).
3. Write the host module in `modules/hosts/<host>/default.nix`:
    ```nix
    { inputs, ... }:
    {
      flake.modules.nixos.<host> = { config, lib, pkgs, ... }:
      {
        imports = [ ./_hardware-configuration.nix ];

        networking.hostName = "<host>";
        networking.networkmanager.enable = true;

        time.timeZone = "America/Sao_Paulo";

        users.users.<user> = {
          isNormalUser = true;
          extraGroups = [ "wheel" "networkmanager" ];
        };

        services.openssh.enable = true;

        nix.settings.experimental-features = [ "nix-command" "flakes" ];

        system.stateVersion = "<release-you-installed-from>";
      };
    }
    ```
    - The outer function takes flake-parts args (`inputs`, `self`, …). The inner function is the actual NixOS module body, from `configurations.nix`.
4. **(Optional)** Wire in Home Manager, if this host should have it. Create `modules/hosts/<host>/home-integration.nix`:
    ```nix
    { inputs, config, ... }:
    {
      flake.modules.nixos.<host> = { ... }:
      {
        imports = [ inputs.home-manager.nixosModules.home-manager ];

        home-manager = {
          useGlobalPkgs = true;
          useUserPackages = true;
          backupFileExtension = "backup";
          users.<user> = {
            imports = [
              config.flake.modules.homeManager.<user-module>
            ];
          };
        };
      };
    }
    ```
    - `config.flake.modules.homeManager.<user-module>` must already exist under `modules/home/`. If the user's HM module doesn't exist yet, create it first:
        ```nix
        # modules/home/user-<user>.nix
        { flake.modules.homeManager.<user-module> = { pkgs, ... }:
          {
            home.username = "<user>";
            home.homeDirectory = "/home/<user>";
            home.stateVersion = "<release-you-installed-from>";
            programs.bash.enable = true;
            programs.git.enable = true;
          };
        }
        ```
5. Register the flake output. Edit `modules/hosts/configurations.nix` and add an entry alongside the existing hosts:
    ```nix
    flake.nixosConfigurations = {
      # ... existing hosts ...

      <host> = inputs.nixpkgs.lib.nixosSystem {
        system = "x86_64-linux";
        specialArgs = { inherit inputs; };
        modules = [ config.flake.modules.nixos.<host> ];
      };
    };
    ```
    - If this host should use a **different nixpkgs** than the rest of the repo, for exemple stable 26.05 while others track unstable, see the "Per-host nixpkgs" section below.
6. Track the files in git. This is not optional for flakes:
    ```bash
    git add modules/hosts/<host>/
    git status --short modules/hosts/<host>/
    ```
    - **Nix `git+file://` flakes only see git-tracked files.** Files on disk but untracked are invisible to every `nix flake` command, including `nix build`, `nix eval`, and `nix flake show`. See [Pitfall #1](#1.-untracked-files-are-invisible-to-flakes).
7. Verify the module registered with `nix eval .#modules.nixos --apply builtins.attrNames`
    - You should see your new host name in the list, alongside the existing ones. If it's missing, **stop** and do not proceed to building. See the Troubleshooting section.
8. Build before switching with `nix build .#nixosConfigurations.<host>.config.system.build.toplevel`
    - A successful build produces a store path. A successful build does **not** guarantee the system will boot cleanly (see [Pitfall #6](#6.-commented-out-lines-in-hardware-configuration.nix-can-break-the-boot-without-breaking-the-build)), but it catches evaluation and module-system errors early.
9. Install and switch. From the target machine from:
    - A NixOS installer, run `sudo nixos-install --flake .#<host>`
    - An already-running NixOS, run `sudo nixos-rebuild switch --flake .#<host>`

### Keep a known-good generation

Before the first `switch` on a machine you don't control physically, make sure you can select an older generation from the systemd-boot menu. If the switch produces a black screen, that's your only reliable way back. `Ctrl+Alt+F3` may not work if the compositor has already died ([Pitfall #7](#7.-booting-a-broken-generation)).

## Per-host nixpkgs

To give one host a different `nixpkgs` input, for exemple, the rest of the repo tracks `nixpkgs` unstable but this host should track `nixpkgs-stable`:
1. **In `flake.nix`**, add a second input:
    ```nix
    nixpkgs-stable.url = "github:NixOS/nixpkgs/nixos-26.05";
    ```
2. **In `modules/hosts/configurations.nix`**:
    ```nix
    <host> = inputs.nixpkgs-stable.lib.nixosSystem {
      system = "x86_64-linux";
      specialArgs = { inherit inputs; };
      modules = [
        config.flake.modules.nixos.<host>
        {
          nixpkgs.pkgs = import inputs.nixpkgs-stable {
            system = "x86_64-linux";
          };
        }
      ];
    };
    ```
    - **Do not** pass `pkgs` through `specialArgs`. It triggers the `specialArgs.pkgs` warning and silently disables `nixpkgs.config`, `nixpkgs.overlays`, and default special args like `modulesPath`. See [Pitfall #3](#3.-never-pass-pkgs-through-specialargs).
3. If this host also uses Home Manager, add a matching HM input for the same release:
    ```nix
    home-manager-stable.url = "github:nix-community/home-manager/release-26.05";
    home-manager-stable.inputs.nixpkgs.follows = "nixpkgs-stable";
    ```
    - Then in `home-integration.nix` for that host, use `inputs.home-manager-stable.nixosModules.home-manager` instead of the unstable one. Home Manager will display warning when its version doesn't match the `nixpkgs` release, and the fix is a matching input. Avoid `home.enableNixpkgsReleaseCheck = false`. See [Pitfall #4](#4.-home-manager-version-must-match-nixpkgs-release).

## Pitfalls

### 1. Untracked files are invisible to flakes

**Symptom:** `nix eval .#modules.nixos --apply builtins.attrNames` doesn't list your new host, even though the file exists on disk. Or `nixosConfigurations.<host>` shows up in `nix flake show` but building it fails with `attribute '<host>' missing`.

**Cause:** `git+file://` flakes copy only tracked files into the store. `import-tree` then walks that copy. If `modules/hosts/<host>/` is untracked, none of its files exist as far as Nix is concerned.

**Fix:**

```bash
git add modules/hosts/<host>/
git status --short modules/hosts/<host>/    # should be empty (all staged)
```

### 2. `import-tree` imports every `.nix` file under `modules/`

**Symptom:** Errors like `The option 'boot' does not exist` or `The option 'fileSystems' does not exist`, pointing at your hardware configuration file.

**Cause:** `import-tree ./modules` treats every `.nix` file under `modules/` as a flake-parts module. `hardware-configuration.nix` contains top-level `boot.*` and `fileSystems.*` declarations, which flake-parts has no options for. It gets evaluated twice: once correctly as a NixOS module (via `imports` in `default.nix`) and once incorrectly as a flake-parts module.

**Fix:** Prefix with an underscore. `import-tree` skips files and directories whose names begin with `_`. Rename the file and update the import:

```bash
git mv modules/hosts/<host>/hardware-configuration.nix \
       modules/hosts/<host>/_hardware-configuration.nix
```

```nix
# in default.nix
imports = [ ./_hardware-configuration.nix ];
```

### 3. Never pass `pkgs` through `specialArgs`

**Symptom:** Warning: *"You have set specialArgs.pkgs, which means that options like nixpkgs.config and nixpkgs.overlays will be ignored."* Followed later by *"argument `modulesPath` is not externally provided"* and an infinite recursion.

**Cause:** Passing `pkgs` through `specialArgs` overrides nixpkgs' own mechanism for providing special args. The module system then falls back to `config._module.args.modulesPath`, which forces `config`, which re-evaluates all modules - infinite loop if any module uses `modulesPath` (which `hardware-configuration.nix` does).

**Fix:** Move `pkgs` out of `specialArgs` and into the module list:

```nix
# Bad
specialArgs = { inherit inputs; pkgs = import inputs.nixpkgs-stable { ... }; };

# Good
modules = [
  config.flake.modules.nixos.<host>
  { nixpkgs.pkgs = import inputs.nixpkgs-stable { system = "x86_64-linux"; }; }
];
```

### 4. Home Manager version must match nixpkgs release

**Symptom:** Warning: *"You are using Home Manager version X and Nixpkgs version Y … mismatched versions."*

**Cause:** Your host uses nixpkgs 26.05 but `home-manager` input tracks master (26.11+).

**Fix:** Add a second `home-manager` input pinned to the matching release branch, and use it only in that host's `home-integration.nix`. Don't silence the warning - it's a real signal.

### 5. Syntax typos silently drop the module

**Symptom:** A file seems to be ignored by `import-tree`, but `git ls-files` shows it tracked.

**Cause:** A parse error. The most common form is `{ inputs: config, ... }:` - using `:` instead of `,` between the function arguments. Nix parses the whole file as a lambda, `import-tree` fails to import it, and the contribution to `flake.modules.*` never lands.

**Fix:** Compare the function head against a working sibling. A correct one looks like:

```nix
{ inputs, config, ... }:
```

### 6. Commented-out lines in `hardware-configuration.nix` can break the boot without breaking the build

**Symptom:** `nix build .#nixosConfigurations.<host>...` succeeds, but after `nixos-rebuild switch` and reboot you get a black screen with a blinking underscore. `Ctrl+Alt+F3` does nothing. `journalctl` from an older generation shows the display manager/compositor crashed silently.

**Cause:** `hardware-configuration.nix` is not just filesystems - it declares `boot.initrd.availableKernelModules`, `boot.kernelModules`, and `boot.kernelParams`. Commenting any of these out (for example while trying to fix something else) builds an initrd without the GPU or storage driver. The system boots far enough to load the compositor, which then fails to open the DRM device and exits. No compositor means no virtual terminal switching.

**Fix:** Never hand-edit `hardware-configuration.nix`. Regenerate it on the target machine with `nixos-generate-config` and copy the result in. If you must edit, review the diff carefully:

```bash
git diff modules/hosts/<host>/_hardware-configuration.nix
```

### 7. Booting a broken generation

If a rebuild produces a system that doesn't start the display manager and `Ctrl+Alt+F3` is unavailable, your recovery options are:

- **From the boot menu**: pick an older generation from the "NixOS - All configurations" submenu. This is the most reliable route.
- **From a root shell** (if you have one): `nixos-rebuild switch --rollback`.
- **From a live USB**: mount the target, `nixos-enter`, then `nixos-rebuild switch --rollback`.

Keeping a known-good generation available is why step 10 matters.

## Reference: file layout for a completed host

```
modules/
├── hosts/
│   ├── configurations.nix              # nixosConfigurations.<host> = ...
│   └── <host>/
│       ├── default.nix                 # flake.modules.nixos.<host> = ...
│       ├── home-integration.nix        # (optional) wires HM into the host
│       └── _hardware-configuration.nix # underscore-prefixed: hidden from import-tree
└── home/
    └── user-<user>.nix                 # flake.modules.homeManager.<user> = ...
```
